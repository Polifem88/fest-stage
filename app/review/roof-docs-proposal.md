## Раздел 1. Обязательное требование заказчика: Регламент проверки паритета (Parity Harness)

> **Правки ревизора (основной агент, 29.10.2026)** — сверено с кодом:
> - в 1.1 было «`caps.ready`» — такого флага нет, речь о `status: 'ready'` (исправлено);
> - в 1.2 было, что сравнивается ключ `layout`, — в `STATE_KEYS` его нет (исправлено, см. 1.6);
> - в 1.4 было имя `dist-master` — так называется старая замороженная сборка от 22.10, ровно источник ошибки; заменено на `dist-<метка>`;
> - добавлены предложения **1.6** (код `parity.mjs`: `capture` только с явным каталогом сборки; `layout` в сравнении состояния) и **1.7** (как новая площадка входит в паритет: её эталон — сборка коммита перевода в `ready`, а у уже готовых площадок — свежий `master`).

### Предложение 1.6. Код `app/scripts/parity.mjs`: эталон только с явной сборки, `layout` в сравнении

- **Файл:** `app/scripts/parity.mjs`
- **Было:** `const distDir = resolve(APP, distArg || (mode === 'capture' ? 'review/modular/baseline/dist-master' : 'dist'));` — без аргумента `capture` молча берёт старую сборку 22.10; `STATE_KEYS` без `layout`.
- **Стало:** `capture` без аргумента завершается с ошибкой и подсказкой («укажите каталог свежей сборки master: npm run build → копия dist → capture <каталог>»); в `manifest.json` и отчёт пишется коммит/дата сборки эталона (если доступен `git rev-parse`). Ключ `layout` добавляется в `STATE_KEYS` при первом переснятии эталона, в котором есть площадка с трансформируемым залом (у Большой и Камерной `layout: null` с обеих сторон).
- **Почему:** самая частая ошибка — «capture» по привычке без аргумента; лучше, чтобы скрипт не позволял её совершить.

### Предложение 1.7. Как новая площадка входит в паритет

- **Файлы:** `GEMINI.md` §4 п. 3, навык `venue-module-authoring` §8–9 (дополнение к 1.1 и 1.3).
- **Стало (текст):** «Площадка в статусе `draft` в паритет не входит. В коммите перевода в `ready` она добавляется в `VENUES` (`app/scripts/parity.mjs`) со своими сценариями экспорта, состояния и, если есть, планировок; эталон переснимается целиком с собранной версии этого коммита (для новой площадки это и есть «последняя версия сцены»), с самопроверкой 100 %. Дальше любые правки ядра сравниваются с этим эталоном, пока следующая площадка не станет `ready` — тогда эталон снова переснимается с актуального `master`.»
- **Почему:** у новой площадки нет версии в `master`, поэтому её эталон — сборка в момент готовности; у уже готовых — свежий `master`.

### 1.1. Инцидент на ветке `roof` и извлечённые уроки

В ходе разработки ветки `roof` выявились три критические проблемы в организации и выполнении паритет-контроля:

1. **Неполнота покрытия площадок (только Большая сцена):**
   Скрипт `app/scripts/parity.mjs` изначально был написан под задачу перехода на модульный движок и проверял исключительно Большую сцену (`big`). При этом правила проекта (`GEMINI.md`, §4.3) декларировали проверку паритета для всех готовых площадок. В результате Камерная сцена (`chamber`, статус `ready`) при изменениях общего ядра (`stage.js`, `state.js`, `testapi.js`, `common.js`) не тестировалась на побайтовую идентичность экспорта DXF/GLB и регресс рендера, что создавало риск скрытой поломки функционала опубликованной сцены.

2. **Ошибочный источник эталона (снятие с устаревшей сборки вместо текущего `master`):**
   Команда `node scripts/parity.mjs capture` по умолчанию читала файлы из каталога `review/modular/baseline/dist-master`, где лежала замороженная сборка от 22.10. Если разработчик вызывал `capture` без параметров, эталон снимался не с текущей кодовой базы `master` (включающей все последние хотфиксы Камерной сцены), а со старого слепка. Сравнение с таким «эталоном» давало ложные расхождения либо пропускало реальные регрессии.

3. **Фантомные визуальные расхождения из-за подсказки жестов телефона (`.mhint`):**
   В мобильном профиле `iphone` на старте показывается подсказка жестов `.mhint`, которая автоматически затухает через 3 секунды. Из-за гонки по времени между стабилизацией сцены и скриншотом полупрозрачный элемент `.mhint` то успевал исчезнуть, то оставался в кадре. Это приводило к превышению порога попиксельного различия ($\Delta > 24$, доля $> 0{,}5\%$) и падению паритета на абсолютно идентичном 3D-рендере.

### 1.2. Что исправлено в скрипте и процедуре паритета

В коммитах `049be67` и `2a30a29` архитектура паритет-харнесса была полностью переработана:
- **Многоплощадочность:** В `parity.mjs` внедрён реестр `VENUES = { big: { ... }, chamber: { ... } }`. Для каждой площадки со статусом `ready` заданы собственные сценарии экспорта (например, `default`, `low`, `onlyRow1`) и состояний. Снимки для сцен вне Большой формируются динамически на основе их паспорта ракурсов (`window.__fest.views`, орто-виды с чертежом/сеткой/размерами, отключённый свет, номера приборов) и фиксируются в манифесте эталона (`manifest.venues[venue]`).
- **Изоляция снимков от UI-оверлеев:** Функция `grabShot` теперь принудительно скрывает `.toast` и `.mhint` (`display = 'none'`), устраняя гонки таймеров.
- **Новый регламент эталонирования (2-шаговый цикл):**
  1. На чистой ветке `master` (или до внесения правок в ядро):
     `npm run build` $\to$ скопировать `dist` в `review/modular/baseline/dist-<метка>` $\to$ `node scripts/parity.mjs capture review/modular/baseline/dist-<метка>`.
  2. **Обязательная самопроверка (Zero-Difference Self-Check):**
     `node scripts/parity.mjs compare review/modular/baseline/dist-<метка>`. Результат обязан быть строго 100% (экспорт 0 diffs, состояние 0 ошибок, снимки 0 расхождений). Только после этого эталон считается легитимным.
  3. После внесения правок в рабочей ветке:
     `npm run build` $\to$ `node scripts/parity.mjs compare` (сравнивает текущую папку `dist` с зафиксированным эталоном).
- **Разделение статусов (`ready` vs `draft`):** Площадки в статусе `draft` (черновик) **не включаются** в `VENUES` скрипта `parity.mjs` во избежание блокировки рефакторинга ядра нестабилизированной сценой. Включение в `VENUES` обязательно производится **в момент перевода площадки в статус `ready`**.
- **Детализированный отчёт:** В отчёте `parity-report.md` и в консоли результаты группируются с явным указанием площадки (`big`, `chamber`).

```markdown

## 6. Устранение неполадок: фантомные имена с пробелом на конце (Trailing Space Issue)

### Проблема:
При распаковке архивов исходных данных от сторонних контрагентов или случайном переименовании в файловой системе NTFS могут появиться папки или файлы с пробелом на конце имени (например, `"Венткороб "` или `"Схема.jpg "`).
- Стандартная подсистема Win32 автоматически обрезает концевые пробелы, поэтому вызовы PowerShell `Get-ChildItem -Recurse` падают с ошибкой `DirectoryNotFoundException` / `ItemNotFoundException`, либо искажают подсчёт файлов.
- В результате скрипт `app/scripts/backup.ps1` завершается аварийно на этапе сверки целостности (`foldersMatch` = false).

### Диагностика:
Поиск повреждённых путей через расширенный синтаксис PowerShell:
```powershell
Get-ChildItem -LiteralPath . -Recurse -Force | Where-Object { $_.Name -match '\s+$' } | Select-Object FullName
```

### Удаление и исправление:
Обычные команды `Remove-Item`, `del` и `rmdir` завершаются ошибкой «Не удается найти указанный файл», так как ОС запрашивает путь без пробела.
Для работы с такими путями необходимо использовать префикс Win32 Device Namespace `\\?\`:

1. **Через командную строку (cmd):**
   ```cmd
   :: Удаление папки с пробелом на конце:
   rd /s /q "\\?\c:\Users\Полифем\antigravity\fest-3dmodels-and-stages\data\roof\Венткороб "

   :: Удаление файла с пробелом на конце:
   del "\\?\c:\Users\Полифем\antigravity\fest-3dmodels-and-stages\data\roof\file.jpg "
   ```
2. **Через PowerShell .NET API:**
   ```powershell
   [System.IO.Directory]::Delete('\\?\c:\Users\Полифем\antigravity\fest-3dmodels-and-stages\data\roof\Венткороб ', $true)
   ```
После устранения некорректных имён `npm run backup` успешно проходит со 100% верификацией.
```
- **Почему:** Практическое решение реальной проблемы файловой системы Windows, блокировавшей проверку бэкапа `backup.ps1`.
