# Разработка модуля площадки (Venue Module Authoring)

Руководство по созданию, конфигурированию, подключению и тестированию модулей сцен и залов в интерактивном каталоге театра «ФЭСТ».

Каждая площадка в проекте представляет собой полностью автономный модуль, расположенный в каталоге `app/src/venues/<театр>-<сцена>/` (например, `fest-big`, `fest-chamber`, `fest-roof`). Модуль экспортирует паспорт площадки по строгому контракту `app/src/venues/contract.js`.

---

## 1. Исходные данные и размещение

1. Все исходные материалы (обмерные чертежи БТИ, проектные PDF, схемы развеса светового цеха, фотографии зала и колосников, замеры лазерным дальномером) сохраняются в каталоге `data/<сцена>/`:
   - `data/big/` — Большая сцена
   - `data/chamber/` — Камерная сцена
   - `data/roof/` — Сцена под крышей
   - `data/foyer/` — Фойе
   - `data/studio/` — Студия мультимедиа
2. Каталог `data/` исключён из Git-индекса (может содержать тяжелые медиаданные и файлы с русскими именами), но **обязательно включается в полный бэкап** (`npm run backup`). В веб-сборку файлы из `data/` не попадают.

---

## 2. Система координат и нулевая линия

Все модули сцен подчиняются единым правилам системы координат Three.js:

1. **Масштаб:** $1 \text{ единица} = 1{,}0 \text{ метр}$.
2. **Ось $Y$ (высота):**
   - $Y = 0$: отметка чистого пола игровой площадки (планшета) данной сцены.
   - Положительный $+Y$ направлен вертикально вверх (к потолку или колосникам).
3. **Ось $Z$ и глубина $d$:**
   - $Z = 0$: **нулевая линия площадки**.
     - Для сцены-коробки с порталом — передняя (зрительская) плоскость портала («красная линия»).
     - Для залов без портала (чёрный кабинет, фойе, студия) — передний край игровой площадки.
     - **Обязательное правило:** выбор нулевой линии фиксируется в шапке `config/dimensions.js`.
   - В Three.js положительный $+Z$ направлен в зрительный зал, отрицательный $-Z$ — в глубину сцены.
   - В объектах конфигурации глубина задаётся как $d = -z$ (положительное $d$ — вглубь сцены, отрицательное $d$ — в зал).
4. **Ось $X$ (ширина):**
   - $X = 0$: продольная ось симметрии игровой площадки и зала.
   - $+X$ — правая сторона (по плану при взгляде со стороны зрительного зала).
   - $-X$ — левая сторона.

## 3. Выбор базового шаблона

В зависимости от архитектурного типа площадки:
- **Чёрный кабинет / зал без подвижной механики:**
  - *Для типовых прямоугольных залов:* используется параметрический шаблон `app/src/venues/_template/` (см. [README.md](../../../app/src/venues/_template/README.md)), где геометрия стен, потолка, ферм, кресел и наложений генерируется готовыми функциями `buildBlackBox`, `blackBoxViews`, `blackBoxOverlays`, `blackBoxAmbient`.
  - *Для залов со сложной архитектурой (несимметричный планшет, карман, ниша выхода, ступенчатый амфитеатр, индивидуальная сетка ферм, кастомные DXF/GLB чертежи):* эталонным производственным образцом служит законченный модуль `app/src/venues/fest-chamber/`.
- **Сцена-коробка с порталом и механикой:**
  Архитектурным образцом служит модуль `app/src/venues/fest-big/` с разделением на подсистемы (`build/architecture.js`, `build/rigging.js`, `build/overlays.js`, `build/ambient.js`, `build/floor.js`).
- **Трансформируемый зал (лофт без портала, станки и стулья по планировкам):**
  Образец — `app/src/venues/fest-roof/`: ортогональный контур помещения из прямоугольников, колонны и капитальные фермы с обрезкой по стенам, сетка ферм 30×30 на жёстком подвесе, сменные планировки зала (`caps.layouts`, `config/layouts.js`), пятна света на полу и верхах станков текущей планировки, экспорт DXF/GLB с текущей планировкой.

## 4. Конфигурационные файлы площадки (`config/`)

Все числовые значения геометрии и оборудования задаются **исключительно** в файлах папки `config/`. «Магические числа» в коде построителей запрещены.

### 4.1. `config/dimensions.js`
Описывает пространственные габариты:
- `room`: внутренний объём (`x0`, `x1` — границы по ширине, `d0`, `d1` — границы по глубине от нулевой линии, `ceiling` — высота потолка).
- `stage`: границы игровой зоны планшета (`d0`, `d1`).
- `hall`: зрительный зал (число рядов `rows`, разбивка на блоки `blocks`, шаг кресел `seatPitch`, глубина ряда `rowPitch`, подъём ступеней `riser`, уровень глаз зрителя `eyeY`).
- `trusses` (при наличии ферм): число ферм `count`, шаг `step`, сечение трубы `tube`, треугольник `side`, отметка нижних поясов `bottomY`.
- `emitters` и `ambient`: точки размещения и параметры яркости дежурного и зального света.
- **Презумпция допущений:** любые размеры, не подтверждённые точными чертежами, снабжаются комментарием `assumption: true`.

### 4.2. `config/rigging.js` (только при `caps.rigging: true`)
Описывает подвижные штанкетные и софитные подъёмы:
- Массив `RIGGING`: объекты вида `{ id: 'Sh1', name: 'Штанкет 1', kind: 'batten', min: 1.2, max: 7.5, rest: 7.2 }`.
- Вид механики `kind` обязан входить в справочник `app/src/library/rigKinds.js` (`batten` — штанкет, `light` — софит, `track` — дорога занавеса, `side` — боковой штанкет).
- Обязательно соблюдение диапазона: `min <= rest && rest <= max`.
- Порядок элементов в массиве является частью формата сохранения ссылок — **новые подъёмы добавляются только в конец**.
- Если на площадке нет подвижной механики, `config/rigging.js` не создаётся, а в паспорте указывается `rigging: null` и `caps.rigging: false`.

### 4.3. `config/fixtures.js`
Описывает спецификацию и развес светового оборудования:
- `TYPES`: словарь используемых моделей. Типы берутся из общего справочника театра `app/src/library/fixtureTypes.js`. Если площадке требуются собственные типы, они подключаются через функцию `venueTypes(localTypes)` — локальные типы обязательно добавляются в конец, чтобы не сдвинуть палитру цветов режима «чертёж».
- `SPECS`: технические паспорта из `app/src/library/specs.js`.
- `GROUPS`: группы приборов с описанием назначения и линий питания.
- `GROUP_SETS`: наборы для кнопок быстрого включения в панели света.
- `BAR_DEPTH`: соответствие между идентификаторами подвижных подъёмов и их глубиной $d$.
- `PORTABLE`: переносные приборы (если `caps.portable: true`, иначе `null`).
- `FIXTURES`: массив `{ no, type, group, mount: { on, x, y, d }, aim: { x, y, d } }`; угол луча берётся из `TYPES[type].beam`. На подвижной трубе `mount.on = '<rig_id>'`: `d` — смещение от `BAR_DEPTH[on]`, `y` — от высоты трубы; на неподвижной конструкции `on: null`, координаты абсолютные. Номера `no` уникальны в пределах площадки; порядок списка — часть формата ссылки (только добавлять в конец).

### 4.4. `config/layouts.js` (только при `caps.layouts: true`)
Трансформируемый зал (образец — `fest-roof/config/layouts.js`):
- `LAYOUTS`: массив планировок `{ id, name, axis: 'd'|'x', rows: [{ rank, x0, x1, d0, d1, h, facing, seats }], pults: [{ kind, x0, x1, d0, d1, h }] }`. **Порядок — часть формата ссылки (`lo[0]`): только добавлять в конец.** `rank` — номер ряда спереди назад («Рядов» убирает ряды с `rank > rows`), `h` — высота станка (0 — стулья на полу), `facing` — куда смотрят зрители.
- `SHIFT_STEP` — шаг сдвига всего зала (рядов и пультов) вдоль `axis`, м; `shiftRange(id, rows) → [min, max]` — допустимые шаги по преградам (колонны, стойки, двери, мольтон, стены) с зазором `CLEAR`; всегда содержит 0.
- `placed(st)` → `{ rows, stands, seats, pults }` — фактическая раскладка (станки 2 × 1, места с шагом) для построителя зала, пола пятен и экспорта; `seatCount(st)`, `rowsMax(id)`.
- `LayoutState = { id, rows, shift }`, `shift` — в шагах. Паспорт (`index.js`) отдаёт `layouts: { list: [{ id, name, rowsMax }], default, shiftStep, range, seats, build(st, { M, profile }) }`.

## 5. Паспорт площадки (`index.js`) и контракт

Файл `app/src/venues/<театр>-<сцена>/index.js` экспортирует объект по контракту `app/src/venues/contract.js`.

### Поля контракта `VenueModule`:

| Поле | Тип | Назначение и требования |
|---|---|---|
| `id` | `string` | Идентификатор площадки (латиница, цифры, дефис, например `'chamber'`). Совпадает с ключом в `catalog.js`, `registry.js` и параметром `#v=<id>`. |
| `name` | `string` | Полное человекочитаемое название («Камерная сцена»). |
| `status` | `'ready' \| 'draft'` | Статус готовности. `'ready'` — выверена; `'draft'` — черновик (открывается, снабжена пометкой). |
| `meta` | `Object` | `{ type: string, seats?: number, note?: string }` — данные для карточки каталога и модального селектора. |
| `caps` | `Capabilities` | Флаги возможностей оборудования (см. ниже). Интерфейс скрывает отсутствующие элементы. |
| `layers` | `Array<[string, string, Object?]>` | Слои сцены `[ключ, подпись, опции]`. Слой `'lights'` обязателен. Порядок = битовая маска ссылки. **Только добавление в конец!** Максимум 30 слоёв. |
| `views` | `Record<string, View>` | Словарь ракурсов. Порядок ключей задаёт порядок кнопок в UI. |
| `defaultView` | `string` | Вид по умолчанию. Обязан существовать во `views` и иметь `type: 'persp'`. |
| `camera` | `Object?` | `{ maxDistance?: number }` — максимальное удаление камеры в метрах. |
| `rigging` | `Object \| null` | `{ list, describe?, controlNames? }` — подвижная механика. Если `caps.rigging === false`, строго `null`. |
| `layouts` | `LayoutsCfg \| null` | Трансформируемый зал при `caps.layouts: true` (`list`, `default`, `shiftStep`, `range`, `seats`, `build`), иначе строго `null`. |
| `fixtures` | `FixturesCfg` | Полная конфигурация света (приборы, типы, группы, пол, обрезка). |
| `lightPlans` | `{ full, lite }` | Группировка источников света для профилей высокой (`full`) и мобильной (`lite`) производительности. |
| `build(ctx)` | `Function` | Функция сборки 3D-сцены через контекст `ctx`. |
| `exports` | `Object` | Функции экспорта `{ planDXF?, sectionDXF?, dxf3d?, glb? }`. Если кастомных DXF нет — `{}` (generic GLB работает автоматически). |
| `texts` | `Object?` | Тексты интерфейса площадки: `{ rigDrag?, extraEquipment? }`. `extraEquipment` — оборудование под спектакль, которого нет в постоянном развесе (блок «📦 Доп. оборудование» внизу панели «Свет»). |

### Флаги возможностей (`caps`):
- `rigging: boolean` — наличие подвижных подъёмов (при `false` скрываются вкладка механики и слайдеры).
- `counterweights: boolean` — канатно-противовесная система (может быть `true` только при `rigging: true`).
- `portable: boolean` — переносные прострельные приборы по планшету (при `false` блок скрывается).
- `duty: boolean` — дежурный рабочий свет сцены.
- `houseLight: boolean` — зальный зрительский свет.
- `layouts: boolean` — трансформируемый зал: вкладка «Зал» (планировки, «Рядов», «Сдвиг»), поле ссылки `lo`, память планировки при смене сцены. Обязательны `layouts` в паспорте и слой `'hall'` — в него движок кладёт группу зала и заменяет её при смене планировки (`Stage.setLayout`: старая группа освобождается, «чертёж» применяется к новой, пятна пересчитываются; пол пятен узнаёт планировку через `fixtures.floor.setLayout(st)`).

### Конфигурация ракурсов (`views`):
1. **Перспективный ракурс (`type: 'persp'`):**
   - `pos: [x, y, d]`, `target: [x, y, d]`
   - `portraitPullback?: boolean | number` — коэффициент или флаг автоматического отдаления камеры в книжной ориентации смартфона.
   - `allRopeLabels?: boolean` — принудительное отображение подписей всех канатов (для галерей).
2. **Ортогональный ракурс (`type: 'ortho'`):**
   - `dir: 'top' | 'side'` — направление проецирования (план сверху или разрез сбоку).
   - `center: [x, y, d]` — центр кадра.
   - `height: number` — видимая высота проекции в метрах.
   - `width?: number` — опциональная ширина проекции.
   - `legendRows?: number` — резервирование места снизу кадра под строки экспликации приборов.

### Конфигурация пола световых приборов (`fixtures.floor`):
Световая система `app/src/systems/fixtures.js` рассчитывает падение лучей и световые пятна через контракт `floor: { trace(p, dir), zone(p), clip(mat) }`:
- **Прямоугольный пол:** используйте хелпер `rectFloor({ x0, x1, d0, d1, y = 0, maxDist = 30 })` из `systems/fixtures.js`.
- **Сложный пол (авансцена со скосами, ступени, перепады):** реализуются собственные методы `trace`, `zone` и `clip`.
  > [!IMPORTANT]
  > В методе `clip(mat)` обязательно задавать **уникальный ключ кэша шейдера**:
  > `mat.customProgramCacheKey = () => 'pool-<id-площадки>'`.
  > Если ключ кэша опустить или продублировать, Three.js повторно использует шейдер первой загруженной сцены, и пятна света будут обрезаться по границам чужого зала (`'pool-chamber'`, `'pool-roof'`).

### Контекст сборки `build(ctx)`:
- `ctx.batch` — пакетный сборщик статики: `batch.add(layerKey, material, geometry | geometry[], { tag?, shadow?, uv? })`, где `material` — объект из `ctx.M`; склеивает геометрию «слой + материал» в один меш (минимум draw calls). После `commitBatch()`/`ctx.add()` добавлять в batch нельзя (движок выдаст ошибку).
- `ctx.commitBatch()` — генерация мешей из накопленных батчей.
- `ctx.add(layerKey, ...objects)` — добавление динамических мешей и групп в конкретный слой.
- `ctx.M` — палитра материалов из `core/materials.js`.
- `ctx.labels` — построитель текстовых меток из `core/labels.js`.
- `ctx.profile` — профиль производительности устройства.
- Метод возвращает объект `{ rigging, emitters, ambient(plan), overlays(labels) }`.

### Продвинутые паттерны (`fest-chamber` / `fest-big`):
1. **Многозонная шейдерная обрезка пятен света (`clipPoolsToFloor`):**
   Когда планшет сцены имеет сложный контур (левый карман $x \in [-8{,}35..-5{,}85]$ при $d \ge 0$ и сужение зала при $d < 0$, плюс ступени амфитеатра), геометрия пятен разделяется через атрибут `aZone` (`0` — планшет $Y=0$, `1` — амфитеатр), а в фрагментном шейдере отбрасываются (`discard`) пиксели за пределами периметра зоны. Обязательно задаётся уникальный `mat.customProgramCacheKey`.
2. **Итеративная трассировка лучей на ступенчатый амфитеатр (`hallFloorY`) и коллизии со стенами:**
   Пересечение луча со ступенчатым полом зала решается 4 итерациями фиксированной точки (`tt = (fy - p.y) / dir.y`), а также проверяется пересечение с ограничивающими плоскостями стен, чтобы лучи прострелов не пробивали внешние стены коробки наружу.
3. **Контракт прямых потомков в `emitters.duty` и `emitters.house`:**
   Меши светящихся элементов (колбы, светодиодные панели, плафоны) **обязаны быть прямыми потомками (`children`)** групп `groups.duty` и `groups.house` с флагом `userData.emitter = 'duty'` / `'house'`, так как `Stage._applyFlags` обходит только прямой массив `g.children` без глубокого `traverse`.
4. **Встроенный набор экспорта (`exports`):**
   Готовая площадка предоставляет 4 генератора: `planDXF`, `sectionDXF`, `dxf3d` и `glb`. У трансформируемого зала экспорт берёт текущую планировку из `stage.layout` (без `stage` — планировку по умолчанию).
5. **Ортогональный контур помещения как объединение прямоугольников (`fest-roof`):**
   Сложный план (выступы, короба, ниши, примыкающий коридор) задаётся набором прямоугольников `rects = [[x0, x1, d0, d1], …]` (≤ 8 — столько же `vec4` уходит в шейдер обрезки пятен), прямоугольники могут перекрываться. `insideRoom(x, d)` — точка в помещении; пол и потолок строятся многоугольником по обходу стен (`roomPolygon`, без перекрытий). Балки, диагонали и швеллеры, уходящие к замурованным колоннам, обрезаются `clipSegmentToRects(a, b, rects)` (`core/geom.js`) — снаружи стен ничего не торчит ни на виде «извне», ни в GLB/DXF.
6. **Динамические верхи станков в обрезке пятен:** пятна ложатся на пол (зона 0) и на верх станков/подиумов текущей планировки (зона 1). Верхи передаются в шейдер uniform-массивами (`uTops`, `uTopH`, `uTopN`), которые `floor.setLayout(st)` обновляет на месте — без перекомпиляции; пиксель зоны 1 сравнивается с высотой станка с допуском. Ключ кэша шейдера уникален (`'pool-roof'`).
7. **Швеллеры под настилом без граней «вверх» (`dropUpFaces`), балки и диагонали — замкнутого квадратного сечения `0,15 × 0,15`:** у швеллеров, подшитых вплотную к настилу, убирается верхняя грань (`Y > 0,9`), чтобы не полосить план сверху; капитальные фермы, X-образные диагонали и V-косынки сохраняют все грани квадратного профиля `0,15 × 0,15` м.
8. **Пустые меши не добавлять:** если у планировки нет деталей (например, «Пустой зал» без станков), меш не создаётся: «чертёж» строит рёбра `EdgesGeometry` по геометрии каждого статического меша, а у геометрии без вершин их не построить.

## 8. Тестирование и верификация

Перед отправкой кода на ревью выполняются следующие проверки:

1. **Контракт площадки:**
   Тест `app/tests/unit/venues.contract.test.js` автоматически находит все открываемые площадки (`isOpenable`) и вызывает `validateVenue()`.
2. **Геометрические тесты площадки:**
   Создаётся отдельный тест `app/tests/unit/<id>.test.js` (по образцу `chamber.test.js`):
   - Проверка габаритов зала и высоты потолка.
   - Проверка шага ферм/подъёмов и их положения в пределах помещения.
   - Проверка уникальности номеров приборов, принадлежности типов к справочнику.
3. **Границы архитектурных модулей:**
   Тест `app/tests/unit/boundaries.test.js` проверяет:
   - Общий код (`engine/`, `systems/`, `ui/`) не импортирует конкретную сцену.
   - Площадка не импортирует другую площадку (кроме `_template/`).
   - В общем коде отсутствуют строковые константы и id созданной сцены.
4. **Визуальные снимки:**
   ```powershell
   $env:VENUE='<id>'; npm run shots
   ```
   Проверяются все сохранённые ракурсы, корректность отрисовки режима «чертёж», читаемость экспликации и наложений.
5. **E2E-тесты и утечки памяти:**
   Тест `app/tests/e2e/venues.spec.js` проверяет:
   - Переключение на новую площадку через селектор в шапке.
   - Открытие по прямой ссылке `#v=<id>`.
   - Отсутствие утечек памяти Three.js (`geometries`, `textures`) при 10-кратном цикле переключения между площадками.
   - Размер всех интерактивных элементов в мобильной версии не менее $44 \times 44$ px.
6. **Паритет готовых площадок (GEMINI.md §4 п. 3):**
   - Пока площадка в `draft`, в паритет (`VENUES` в `app/scripts/parity.mjs`) она не входит.
   - В коммите перевода в `ready`: добавить площадку в `VENUES` (сценарии экспорта и состояния по образцу `chamber`; у трансформируемого зала — `layouts: true` и сценарии планировок), переснять эталон целиком со сборки этого коммита (`npm run build` → копия `dist` в `review/modular/baseline/dist-<метка>` → `capture <каталог>`), самопроверка `compare <каталог>` = 100 %, затем `compare` текущей сборки. `tests/unit/parity-config.test.js` упадёт, если готовая площадка не попала в `VENUES`.
   - Правки общего кода и экспорта, затрагивающие готовые площадки, — вместе с правкой и проверкой `parity.mjs`.
